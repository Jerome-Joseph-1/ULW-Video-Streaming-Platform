# 0039. OpenMLS behind a narrow C API, pinned by Cargo.lock

Status: Accepted
Date: 2026-09-29

## Context

ADR-0016 chose MLS through OpenMLS, a Rust library. The server never holds keys, so it needs no
MLS at all; what needs it is everything that plays a client: the tests that prove the key package
directory and commit ordering work with real MLS messages, fuzzing of the parsers a client
exposes, and the client harness. Those are C++. The bridge must not become a way for Rust panics,
Rust ownership or Rust types to leak into C++, and it must build in CI without fetching anything
unpinned (hard boundary 6), under the ASan preset as well.

## Options

| Option | Why it was tempting | Verdict |
|---|---|---|
| A small `extern "C"` crate with opaque handles and status codes, built by cargo from CMake | One narrow, auditable seam; the C header is generated from the Rust source and checked | Accepted |
| The `cxx` crate for a typed C++/Rust bridge | Richer types across the boundary, no raw pointers | Rejected: another code generator in the build, and C++ types in the API tie the client harness to C++ |
| Corrosion to import the crate into CMake | Maps cargo targets to CMake targets | Rejected: one more pinned dependency to import a single static library; an `add_custom_command` does it in 20 lines |
| An MLS implementation in C or C++ (mlspp) | No Rust toolchain | Rejected: ADR-0016 chose OpenMLS, which is what the browser client will run as WebAssembly, so tests exercise the same code |
| Vendoring every crate into the repository (`cargo vendor`) | Builds with no registry at all | Rejected for now: about 200 crates of source in the tree. Cargo.lock already pins each by version and SHA-256 |

## Decision

- `infra/e2ee/mls_ffi_bridge` is a `staticlib` crate exposing fifteen functions:
  client and group handles, key packages, create, join, add, remove, merge or clear a pending
  commit, encrypt, process, epoch and member count. Every function returns a `UlwMlsStatus`,
  checks every pointer, writes outputs only on success and runs inside `catch_unwind`, so no
  panic crosses into C. Byte results are Rust-allocated `UlwMlsBuffer`s released by
  `ulw_mls_buffer_free`; inputs are borrowed for the call.
- A group's own commit stays pending until the caller merges it (the directory accepted it for
  the epoch, ADR-0038) or clears it (another commit won); commits from others are merged as they
  are processed.
- Ciphersuite `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, the one RFC 9420 makes mandatory,
  through `openmls_rust_crypto`: pure Rust (RustCrypto), so the build needs no C toolchain or
  assembler for crypto. `openmls_libcrux_crypto` is formally verified and faster, and can
  replace it behind the same API once it has had a few more releases.
- `include/ulw/mls_ffi_bridge.h` is generated by cbindgen from `src/lib.rs`; `cargo test` fails
  when the committed header differs, and `ULW_BLESS_HEADER=1 cargo test` regenerates it.
- `infra/e2ee` holds the C++ RAII wrapper (`ulw::e2ee_mls`): `MlsClient` and `MlsGroup` own
  their handles, and every call returns `std::expected`.
- Pinning: `Cargo.toml` names exact versions (`openmls =0.9.0`, `openmls_rust_crypto`,
  `openmls_basic_credential` and `openmls_traits =0.6.0`); the committed `Cargo.lock` pins the
  whole graph, each crate with the SHA-256 cargo checks on download and on every build.
  `rust-toolchain.toml` pins rustc 1.94.1 with the minimal profile, which rustup verifies
  against its signed manifest; clippy and rustfmt are added by the lint job, which is the only
  thing that uses them. CMake builds with `cargo build --release --locked --offline` and
  `RUSTUP_AUTO_INSTALL=0`: the build never resolves or downloads anything, a toolchain included,
  and a machine without the pinned toolchain fails loudly. The one networked step is the
  `mls_ffi_fetch` target (or CI's setup action): `rustup toolchain install` and
  `cargo fetch --locked`, which fills the registry cache from the lock file alone.
- The Rust side always builds with the release profile and is not instrumented. Under the asan
  preset, ASan and LeakSanitizer still see every allocation Rust makes, since Rust allocates
  through the same `malloc`, and the C++ side is fully instrumented. `-Zsanitizer=address` would
  instrument Rust too but needs a nightly toolchain, which the pinning rules out.
- The bridge runs on the caller's thread only and never starts one, which is also what the
  reactor model expects of anything a loop thread calls. OpenMLS computes update paths with
  rayon's parallel iterators, unconditionally outside wasm, and those would start rayon's
  global pool of one thread per CPU. So each calling thread becomes the sole worker of a
  one-thread rayon pool of its own (`use_current_thread`), and every call runs inside it; the
  parallel iterators then run in place. A test counts `/proc/self/task` around a full cycle.
  rayon leaks such a pool once per calling thread, a few hundred bytes.
- `ULW_BUILD_MLS` defaults to `ULW_BUILD_TESTS`: production images build without tests and so
  without cargo.

## Consequences

- CI needs cargo and one `cargo fetch --locked` before configuring; a machine without the fetched
  registry fails the build with cargo's offline error rather than downloading.
- The bridge is for harnesses: a handle is used by one thread at a time, and a client's state
  lives in memory only.
- A tampered copy of a message that reaches content decryption spends that generation's key, so
  the genuine message is then undecryptable (RFC 9420 deletes keys once used). A server that
  can drop messages could do as much anyway; the room owner forwards what the sender sent.
- Multi-device key management remains the gap ADR-0016 names: every device is a separate member
  with its own credential, nothing binds a user's devices together, a new device reads nothing
  from before it joined, and adding one needs a commit from a device already in each group.
- Reopen when libcrux is mature enough to replace RustCrypto, or if the harness needs persistent
  client state.
