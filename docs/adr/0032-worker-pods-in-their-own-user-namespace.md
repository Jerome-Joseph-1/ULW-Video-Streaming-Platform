# 0032. The worker pod runs in its own user namespace with a derived seccomp profile

Status: Accepted, amended by 0088 (the profile is `deploy/kubernetes/cluster/seccomp/ulw-worker.json`)
Date: 2026-09-29

## Context

`ulw_sandbox` (ADR-0025) starts every ffmpeg in new user, network, mount and pid namespaces and
mounts a `/proc` for the new pid namespace. In the sandbox cluster the worker, as an ordinary
non-root pod with the runtime's default seccomp profile, fails its start-up check:
`unshare with a user namespace: Operation not permitted`. With seccomp `Unconfined` it gets one
step further and fails at `mount /proc: Operation not permitted`, because a container's `/proc`
has masked paths and the kernel refuses a new proc mount that would reveal them. The worker must
not run ffmpeg without the sandbox.

## Options

| Option | Why it was tempting | Verdict |
|---|---|---|
| Run the worker privileged, or as root with `CAP_SYS_ADMIN` | The sandbox's direct path; no cluster features needed | Rejected: a decoder exploit that escaped ffmpeg's namespaces would hold real root capabilities on the node |
| seccomp `Unconfined` plus an unmasked `/proc` | Two settings | Rejected: it drops the syscall filter for ffmpeg too, the process parsing hostile input |
| Drop the pid namespace and its `/proc` from the sandbox | No `/proc` mount needed | Rejected: the pid namespace is what guarantees nothing ffmpeg starts outlives it (ADR-0025) |
| A pod user namespace (`hostUsers: false`), `procMount: Unmasked`, and a Localhost seccomp profile: the runtime default plus `unshare`, `mount` and `mount_setattr` | Every id in the pod, root included, is unprivileged on the node; the filter stays on for everything else | Accepted |

## Decision

- video-worker sets `hostUsers: false`, `procMount: Unmasked` on its container, and
  `seccompProfile: Localhost` with `profiles/ulw-worker.json`.
- `deploy/askedin/seccomp/ulw-worker.json` is generated by `deploy/local/seccomp-profile.py`
  from Docker's default profile, pinned by commit and SHA-256. Docker's conditional rules are
  evaluated for the worker's container (x86-64, no capabilities) because the kubelet passes a
  Localhost profile to the runtime as a plain OCI profile and would ignore the conditions,
  allowing every conditional syscall.
- The profile is installed on the node once, at
  `/var/lib/kubelet/seccomp/profiles/ulw-worker.json`.

## Consequences

- The cluster needs user namespaces for pods: Kubernetes 1.33 or later (or the
  `UserNamespacesSupport` feature gate), a kernel with idmapped mounts for the node's filesystems
  (6.3 or later for overlayfs), and a containerd and runc that support them. RUNBOOK.md lists
  the checks. Verified in the sandbox (Kubernetes 1.37, kernel 6.18).
- A pod can mount inside its own namespaces; the kernel confines those mounts to the pod's user
  namespace. The seccomp profile must be regenerated when the upstream default changes in a way
  that matters (new syscalls that ffmpeg or glibc start using).
- A missing profile file keeps the pod in `CreateContainerError`; a missing user-namespace
  feature fails the worker's own start-up check. Neither runs ffmpeg unconfined.
- Reopen if the sandbox helper gains a mode that needs no new `/proc`, or K3s on k8s-prod cannot
  run pods in user namespaces.
